# HIOP — Feature Improvements and Development Requirements

## 1. Naming Rules

- Restore the previous manual naming-rule configuration screen.
- Remove the DT, LT, POS, and SC shortcut buttons.
- Remove the automatic hostname-to-device-code mapping.
- Fix the UUID error that occurs after selecting a hostname code.
- Do not introduce a new naming algorithm until the naming-rule logic is agreed upon.

### Required Naming-Rule Logic

Keep naming rules simple, flexible, and user-defined. The interface should allow administrators to create multiple rules using the following format:

**Where:** `__________` **=** `__________`

Examples:
- Where `LT` = Laptop
- Where `POS` = Point of Sale Terminal
- Where `PRN` = Printer
- Where `CAM` = Camera

Requirements:
- Allow users to create, edit, and delete multiple naming rules.
- Rules must be case-insensitive. For example, `LT`, `Lt`, and `lt` should match equally.
- Apply rules to hostname data to help identify and classify devices.
- Display the matching rule and the evidence behind the classification.
- Avoid guessing when no rule matches.
- Keep naming rules separate from device approval and inventory processes.

## 2. Monitoring Wording

Replace the message:

“HIOP is sending checks to the local agent.”

With wording that accurately describes the architecture.

The desktop application itself acts as the local service. The interface should explain that HIOP is checking devices on the local network.

Suggested wording:

“HIOP is monitoring devices on your local network.”

Ensure that monitoring messages accurately reflect the actual service status and do not claim that checks are running when they are not.

## 3. Automate Features and Status Reporting

Complete and verify the following automation features before presenting them as active:

- Email notifications.
- Daily audit-log email delivery.
- Automatic offline-incident detection.

Requirements:
- Display the actual operational status of each feature.
- Distinguish between enabled, running, failed, and not configured states where applicable.
- Show the last successful execution or delivery time.
- Display understandable error messages when a feature cannot run.
- Provide actionable guidance for resolving configuration or delivery failures.
- Do not display a successful or active status unless the feature is genuinely working.

## 4. Audit Log Improvements

Add filtering options to the Audit Log page.

Required filters:
- Date range.
- User.
- Action.
- HIOP area or module.
- Outcome or status.
- Property or organization.

Requirements:
- Allow multiple filters to be applied together.
- Provide a clear way to reset filters.
- Display readable descriptions of recorded actions.
- Include relevant timestamps and the user responsible.
- Record device approvals, alert acknowledgements, alert resolutions, and other important administrative actions.
- Ensure the filtered results can be exported where supported.

## 5. This Computer — Local Operations Dashboard

Redesign the This Computer page as a practical dashboard for monitoring and managing the local HIOP installation.

### Information to display

- **HIOP service:** Running, stopped, or failed.
- **Private database:** Available, unavailable, or experiencing an error.
- **Network information:** Current network connection and local IP address.
- **Last discovery scan:** Date, time, and result.
- **Monitored devices:** Total number of monitored devices.
- **Backup status:** Last backup, result, and next scheduled backup where applicable.
- **Storage status:** Available disk space and database or application storage usage.
- **Recent errors:** Important service or database errors in plain language.

### Quick actions

- Run device discovery.
- Open HIOP settings.
- View service diagnostics.
- Create or download a support report.
- View backup and recovery information.

The page should help an administrator quickly determine whether HIOP is operating correctly and what action is required when a problem occurs.

## 6. Organization Reports

Simplify the main Organization Reports page.

Requirements:
- Display only a small number of commonly used report options initially.
- Provide one simple date-range filter.
- Keep the export action clearly visible.
- Hide advanced filters until the user requests them.
- Keep the interface easy to understand for non-technical hotel staff.
- Preserve access to advanced reporting functionality without cluttering the main page.

## 7. End-to-End Alert Management

Verify that the complete alert lifecycle works correctly.

### Required workflow

1. A configured monitoring condition occurs.
2. HIOP detects the condition and generates an alert.
3. The alert appears on the Alerts page.
4. An authorized organization administrator can acknowledge the alert.
5. The administrator can resolve the alert when the underlying condition has been addressed.
6. Both acknowledgement and resolution are recorded in the audit history.

Additional requirements:
- Display the device, alert type, severity, timestamp, and current status.
- Distinguish between active, acknowledged, and resolved alerts.
- Preserve alert history for auditing.
- Prevent unauthorized users from performing administrative actions.
- Show clear errors when an alert action fails.
- Test the complete workflow rather than only verifying that the Alerts page loads.

## 8. Remove SNMP and Network Topology

Temporarily remove SNMP and network topology functionality from HIOP.

Requirements:
- Remove the corresponding pages and navigation items.
- Remove associated user-facing functions and controls.
- Remove obsolete dependencies or background processes where safe and appropriate.
- Ensure that removing these features does not break device discovery, inventory, reporting, or other required functionality.

SNMP-based inventory collection may be reconsidered later as part of the optional detailed inventory feature described in Section 13.

## 9. Persistent Desktop Sign-In

Improve desktop authentication so users can remain signed in for approximately one hour without repeatedly entering their credentials.

Requirements:
- Implement an appropriate session lifetime of approximately 60 minutes.
- Maintain the session securely across normal application navigation and refreshes.
- Use secure session or token handling appropriate to the desktop architecture.
- Expire sessions correctly and require reauthentication when necessary.
- Provide a clear sign-out option.
- Respect administrator policies and permissions.
- Avoid storing passwords in plain text or exposing authentication tokens in logs.

## 10. Improved Network Device Discovery

Improve HIOP's local network discovery so it identifies more devices safely, including devices that do not respond to ping.

### Discovery evidence

Use multiple sources of evidence where available:

- ARP cache and operating-system neighbour tables.
- Hostname and IP address information.
- MAC address and vendor identification.
- Configured, authorized network probes.
- Open-service detection using appropriate connection checks.
- Device response details and discovery timestamps.

### Device classification

Identify common device categories only when supported by evidence, including:

- Laptops and desktop computers.
- Servers.
- Printers.
- POS terminals.
- Cameras and CCTV equipment.
- Network switches.
- Firewalls and other security devices.
- Other network-connected equipment.

### Evidence-based identification

For each discovered device, display:
- The proposed device type.
- The evidence used to identify it.
- The source of each relevant data point.
- The confidence or certainty of the classification, where practical.
- Any information that remains unknown.

For example, a hostname containing `LT` may support a laptop classification if it matches a configured naming rule. A vendor identifier or an observed service may provide additional evidence.

Do not classify devices solely from an unverified hostname pattern.

### Safety and reliability

- Keep discovery limited to authorized networks.
- Use conservative scanning settings and configurable scan limits.
- Avoid disruptive probes.
- Handle devices that block ping or restrict access gracefully.
- Do not treat an unanswered ping as proof that a device is offline.
- Clearly distinguish between discovered devices, monitored devices, and approved inventory records.

## 11. Optional Detailed Device Inventory and Serial Numbers

Introduce detailed inventory collection as a later, optional capability.

### Supported collection methods

- **Windows devices:** Approved WMI or WinRM access.
- **Printers, switches, firewalls, and UPS devices:** SNMP, if reintroduced and explicitly configured.
- **Linux devices:** Restricted SSH access.

### Requirements

- Make detailed collection optional and configurable.
- Require appropriate credentials and authorization.
- Collect only the information needed for inventory.
- Display the collection method and collection date.
- Store serial numbers only when they can be verified.
- Leave the serial number blank when it cannot be retrieved or verified.
- Display collection failures without marking the entire device record as invalid.
- Protect credentials and prevent secrets from appearing in logs or support reports.

Basic discovery must continue to work even when detailed inventory access is unavailable.

## 12. Device Actions Menu

Add an Actions menu to each device record.

### Required actions

- Ping the device.
- Run a traceroute.
- Open the device's HTTP or HTTPS address when available.
- Launch an RDP connection where supported.
- Launch an SSH connection where supported.
- Rescan the device.
- Copy the IP address.
- Copy the hostname.
- Copy the MAC address.

Requirements:
- Show only applicable actions when the necessary information is available.
- Display clear errors when an action cannot be completed.
- Avoid silently failing actions.
- Validate addresses and use the operating system's supported handlers where appropriate.
- Require appropriate permissions for privileged actions.

### Remote control and file transfer

Do not build a separate remote-control or file-transfer system into this feature by default.

Instead, integrate with an approved tool already used by the hotel, such as Radmin, AnyDesk, or TeamViewer, subject to authorization, licensing, and security requirements.

## 13. Improved Device Export

Improve inventory export functionality.

### Export options

Allow users to choose:
- The first 50 devices.
- The first 100 devices.
- All devices in the filtered result set.

Requirements:
- Export the complete selected device records, not merely the currently visible table rows.
- Respect active search criteria and filters.
- Make the selected export count clear before generating the file.
- Handle large exports without freezing the desktop application.

### Supported formats

- Word inventory reports.
- CSV files.
- Excel workbooks.

### Word report formatting

- Use landscape page orientation.
- Use readable column widths and font sizes.
- Repeat table headings on subsequent pages.
- Prevent important device information from being unnecessarily truncated.
- Include suitable report titles, generation dates, and relevant filter details.

## 14. Local Support and Recovery

Add a dedicated support and recovery area.

### Information to display

- HIOP service status.
- Private database availability.
- Recent startup errors explained in plain language.
- Backup status and the most recent backup result.
- Restore capability and the latest restore status, where available.
- Relevant diagnostic information for troubleshooting.

### Support report

Provide a safe way to generate and download a support report containing relevant diagnostic details.

Requirements:
- Exclude passwords, authentication tokens, private keys, and other secrets.
- Avoid unnecessarily exposing sensitive device or network information.
- Clearly indicate what information the report contains.
- Explain how to share the report safely with authorized support personnel.

### Recovery

- Provide clear guidance when the service or database fails.
- Validate backups before treating them as usable recovery points.
- Confirm the target and consequences before a restore operation.
- Avoid destructive recovery actions without explicit administrator confirmation.
- Record important recovery operations in the audit log where applicable.

## 15. Device Approval

Fix device approval so an organization administrator can approve any discovered device that meets the inventory eligibility requirements.

### Required behavior

- Allow eligible discovered devices to be approved by an authorized organization administrator.
- Clearly explain why approval is unavailable when a device is ineligible or the action is unauthorized.
- Never display an enabled-looking approval button that fails silently.
- Preserve the device's hostname, IP address, MAC address, type, and supporting discovery evidence after approval.
- Record the approving administrator and approval date in the audit log.
- Prevent duplicate or inconsistent inventory records when approving a device more than once.
- Display success or failure feedback after the action.

### Device Details page

Replace raw technical JSON with readable labels and values.

Present information in logical sections, such as:
- Device identity.
- Network information.
- Device classification.
- Discovery evidence.
- Inventory details.
- Approval status.
- Scan history.

Keep advanced technical details available in a separate expandable section when needed for troubleshooting.

## 16. Import Existing Inventory and HIOP-Based Device Matching

Allow users to upload existing inventory documents to improve HIOP's ability to identify discovered devices.

### Supported input formats

- CSV.
- Excel workbooks.
- Word documents.

### Import workflow

1. The user selects an inventory file.
2. HIOP previews the available data and identifies the columns or fields it can recognize.
3. The user maps relevant fields, such as hostname, IP address, MAC address, device type, property, and serial number.
4. HIOP validates the records and identifies missing or conflicting information.
5. HIOP compares the imported inventory with discovered devices.
6. HIOP displays matched, unmatched, and ambiguous records for review.
7. The user confirms the import and matching results.

### Matching requirements

- Use hostname as an important matching signal.
- Use MAC address, IP address, serial number, and other verified identifiers where available.
- Normalize hostname comparisons to be case-insensitive.
- Allow configurable naming rules to help interpret hostname patterns.
- Do not automatically merge records based solely on a hostname match when conflicting evidence exists.
- Avoid creating duplicate device records.
- Preserve the original imported data and its source where appropriate.
- Clearly explain why a device was matched or left unidentified.
- Allow authorized users to correct or confirm uncertain matches.

Imported data should improve device identification without being treated as proof that a device has been verified on the network.

## 17. HIOP Agent for Remote Device Management

Design a dedicated HIOP agent that can be installed on authorized hotel systems to extend monitoring and inventory capabilities.

### Objectives

- Enable HIOP to collect additional information from managed devices.
- Support more reliable hostname and device identification.
- Provide device health and status information.
- Enable authorized inventory collection beyond what network discovery can obtain.
- Support controlled remote administration through approved and secure mechanisms.

### Agent requirements

- Provide an installation package suitable for supported operating systems.
- Establish a secure, authenticated connection between the agent and the HIOP desktop service or approved backend.
- Require explicit enrollment or administrator authorization before a device becomes managed.
- Display agent installation, connection, and health status in HIOP.
- Support secure updates, error reporting, and removal.
- Use least-privilege permissions.
- Encrypt communications and protect credentials.
- Maintain an auditable record of administrative actions.
- Require authorization for remote commands and sensitive operations.
- Do not implement hidden access, unrestricted remote command execution, or unapproved file transfer.

Remote control and file transfer should use an approved hotel tool unless a separately reviewed and explicitly authorized capability is implemented.

## 18. Implementation and Acceptance Requirements

Before presenting any feature as complete, verify its behavior in the running application.

For every feature:
- Confirm that the interface is connected to the actual backend functionality.
- Test successful operation and expected failure scenarios.
- Show truthful status information.
- Provide useful error messages.
- Enforce user roles and organization boundaries.
- Record relevant administrative actions in the audit log.
- Avoid placeholder controls that appear functional but do nothing.
- Preserve existing working functionality unless its removal is explicitly required.

Prioritize the work in manageable stages:

1. Restore naming rules and fix the UUID error.
2. Correct monitoring wording and remove SNMP/topology pages.
3. Complete alerts, automation status reporting, and audit-log filters.
4. Improve the This Computer dashboard and support diagnostics.
5. Fix device approval and implement safer, evidence-based discovery.
6. Improve reports, inventory imports, and exports.
7. Add device actions and persistent desktop sign-in.
8. Plan and implement detailed inventory collection and the HIOP agent with appropriate security controls.

The priority is a reliable, understandable, and secure HIOP application—not merely an interface that appears complete.
